# DECISIONS.md 

1. **Indexes.** Which indexes did you create, and which query or guarantee does each one serve? Which one did you consider and reject?
I created six indexes. `employees.emp_code` (unique) enforces the business code and makes concurrent creates return one 201 and the rest 409. `employees.(department, emp_code)` serves `GET /employees` filtered by department and sorted by emp_code. `attendance_logs.(emp_code, date)` (unique) enforces one record per employee per day and makes concurrent punch-ins race-safe. `attendance_logs.(date desc, emp_code asc)` serves `GET /attendance` with its default sort. `attendance_logs.(emp_code, date, status)` and `attendance_logs.(emp_code, date, late_minutes desc)` serve the analytics filters and leaderboard totals. `attendance_logs.(status, date)` serves the department summary and trend. I rejected a single `date`-only index because the list endpoint sorts by `(date desc, emp_code asc)` and a compound index avoids an in-memory sort.

2. **Punch-in race.** Two identical punch-in requests arrive at the same instant. Walk through exactly what happens in your code.
Both requests hit `POST /attendance/punch-in` for the same `(emp_code, date)`. Both call `find_one` first and see no document, so both try `insert_one`. The first insert succeeds and returns 201. The second insert violates the unique index on `(emp_code, date)`; PyMongo raises `DuplicateKeyError`, which I catch and convert to 409. No check-then-insert race survives because the database, not the application, is the arbiter.
3. **Ties.** Two employees are tied on late minutes at the cutoff of `limit`. What does your leaderboard return, and why?
The leaderboard uses `$setWindowFields` with `$rank`, which is standard competition ranking: tied employees share the rank, and the next rank is skipped (1, 2, 2, 4). Because `limit` is applied with `$match: {rank: {$lte: limit}}` after ranking, a tie at the cutoff returns *all* tied employees — the response can contain more rows than `limit`. Rows inside a tie are ordered by `emp_code` ascending via the final `$sort`.
4. **Headcount.** How does your department summary make sure employees with zero logs are counted?
The department summary starts from the `employees` collection with `joined_on <= last day of the month` (R9), then `$lookup`s the logs. A `$unwind` with `preserveNullAndEmptyArrays: true` keeps employees who have no logs at all, so `$addToSet: "$emp_code"` counts them. Departments whose headcount is 0 for the month are dropped with a final `$match` on `headcount > 0`.
5. **One thing you would change** if this had to serve 100x the data.
Two changes. First, precompute the daily aggregates into a separate collection keyed by `(department, date)` and update it incrementally on punch-in/out, so the trend and summary endpoints read small pre-aggregated docs instead of scanning logs. Second, replace the `$lookup` on `employees` in the leaderboard and summary with a materialised `department` field on each log (denormalised at write time), removing the cross-collection join entirely.
